# Piper TTS Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a CPU-efficient Piper neural TTS engine with a bundled, license-safe en-US voice while preserving espeak-ng as the fallback.

**Architecture:** Bundle `libpiper` + ONNX Runtime + the `en_US-ljspeech-medium` model in the Flatpak. A `PiperEngine` implements the existing `TtsEngine` interface, loads the model once on the worker thread, and streams float32 22,050 Hz samples to the existing `AudioBuffer`. A thin backend interface keeps host tests independent of ONNX Runtime; `PluginContext` selects Piper or espeak and falls back when Piper is unavailable.

**Tech Stack:** C++17, Qt6, CMake/Ninja, Flatpak, `OHF-Voice/piper1-gpl` `libpiper` C API, ONNX Runtime CPU, espeak-ng, Go helper unchanged.

**Spec:** [`docs/superpowers/specs/2026-10-21-piper-tts-design.md`](../specs/2026-10-21-piper-tts-design.md)

## Global Constraints

- Target: OBS Studio Flatpak 32.2.2; extension ID `com.obsproject.Studio.Plugin.YtChatTts`; prefix `/app/plugins/YtChatTts`; module ID `yt-chat-tts`.
- CPU-only; no GPU/CUDA, cloud TTS, Python inside OBS, or runtime network dependency.
- Piper voice: `en_US-ljspeech-medium` only; 22,050 Hz mono float; LJSpeech public-domain model card.
- Model loaded once per worker; no per-message model/process load.
- Audio remains 22,050 Hz mono float; `AudioBuffer::pop` owns volume/clamping; OBS source/queue/filter/helper protocols unchanged.
- No blocking model load on the Qt/OBS UI thread; Piper runs on the existing TTS worker thread.
- Rate maps to `lengthScale = 165 / rate`, clamped to `0.5–2.0`.
- No `lessac` model or other research/non-commercial voice may be bundled.
- No writes outside repo/build dirs and the plugin config directory; no API key changes.
- All new third-party code/model/license files must be installed in the extension and documented.

## Review Focus

- **Missing/corrupt model or ONNX runtime:** user must hear espeak fallback and see a clear log, never silence or a crash.
- **Cancellation during synthesis:** Stop/unload must not hang the UI or leave a Piper session/model stuck.
- **Rate mapping:** 80–450 UI rate must produce valid clamped `length_scale`; no divide-by-zero or extreme values.
- **Sample rate:** any non-22,050 Hz output must be rejected with a clear error; no mis-pitched audio.
- **Packaging:** the Flatpak must build offline from pinned sources, contain Piper/ONNX/model/espeak data, and have no missing shared libraries.
- **CPU/latency:** first load is allowed once; steady-state 200-character synthesis must be under 1.5 s on the reference CPU and must not reload the model per message.

class PiperApi {
public:
    virtual ~PiperApi() = default;
    virtual bool synthesize(const QString &text, float lengthScale,
                            std::vector<float> *pcm, int *sampleRate,
                            QString *error) = 0;
    virtual void cancel() = 0;

public:
    PiperEngine(std::unique_ptr<PiperApi> api, int rate = 165);
    bool synthesize(const QString &text, std::vector<float> *pcm,

    void cancel() override;

};

- [ ] **Step 2: Implement `PiperEngine`**

  - return false on API failure or a sample rate other than 22,050;
  - forward `cancel()` and `resetCancel()` to the API.

### Task 3: Implement the real libpiper backend

**Files:**
- Create: `src/libpiper-api.hpp`
- Create: `src/libpiper-api.cpp`
- Modify: `src/piper-engine.*`
- Modify: `CMakeLists.txt`
- Modify: `tools/piper_probe.cpp` (use the real backend if useful)

**Interfaces:**
- Produces: `LibPiperApi : PiperApi`, owning a lazily created `piper_synthesizer*`.
- Consumes: `libpiper` headers/library and the model/config/espeak-data paths.

- [ ] **Step 1: Implement model loading on first synthesis**

`LibPiperApi` constructor stores model/config/espeak data paths. On the first `synthesize`:
  - call `piper_create` with the three paths;
  - on failure return false with a descriptive error;
  - keep the synthesizer for later utterances.

- [ ] **Step 2: Implement synthesis and cancellation**

Use `piper_synthesize_start` with `piper_default_synthesize_options`, set `length_scale`, then loop over `piper_synthesize_next`:
  - append `chunk.samples` for `chunk.num_samples`;
  - record `chunk.sample_rate` and reject a non-22,050 rate;
  - check an atomic `cancel_` between chunks; on cancel return false with `"cancelled"`;
  - return false on a libpiper error or empty output.

`cancel()` only sets the atomic flag. `resetCancel()` clears it. The model must not be destroyed/reloaded between messages.

- [ ] **Step 3: Link the real backend**

In CMake, when `libpiper` is available, add `src/libpiper-api.cpp` to the plugin and link `piper` and `onnxruntime`. Keep the host test target using only the fake API.
